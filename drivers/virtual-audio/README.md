# Audiora Virtual Audio

Audiora's own Windows audio driver. Once installed, Windows (Settings → System → Sound, and every
program's device list) shows:

| Endpoint | Kind | What it is for |
|---|---|---|
| Audiora Game / Chat / Media / Aux | output | Pick one in a program (or let Audiora route the program there). The engine mixes each one into its channel strip. |
| Audiora Mic Feed | output | The engine plays the processed microphone here. Not meant to be picked by hand. |
| Audiora Microphone | input | Pick this in Discord, Chrome, OBS, games: it is your microphone after Audiora's voice chain. |

Everything runs on Audiora's own driver; no third-party software is involved.

Status: **works on a test machine** (2026-10-26, Hyper-V Windows 11 VM, test-signed 0.1.1.0): the
driver loads, all six endpoints appear with their names, and `audiora.exe cabletest` passes: a
1 kHz tone at -15.1 dBFS RMS played into Audiora Mic Feed arrives at Audiora Microphone at
-15.1 dBFS RMS, 999.8 Hz, no gaps, first audio after 73 ms. Not yet run under Driver Verifier or for
long periods; see [DESIGN.md](DESIGN.md#verification-before-any-release) before giving it to anyone.

Note for testing in a VM: an Enhanced Session (Remote Desktop) shows only "Remote Audio"; use the
basic console connection to see and use the Audiora endpoints.

## How it works (v1)

The source is Microsoft's SimpleAudioSample (MS-PL, see `LICENSE-MS-PL.txt`; Microsoft's copyright
headers are kept), changed in a few places:

* `Source/Filters/minipairs.h`: six endpoints instead of a speaker and a mic array.
* `Source/Filters/speakertoptable.h`: one topology filter per output, each with its own name GUID
  (that is how Windows gets the names "Audiora Game", ...).
* `Source/Filters/speakerwavtable.h`: every endpoint uses 48 kHz / 32-bit PCM / stereo.
* `Source/Main/cable.{h,cpp}`: the **mic cable**, a 1 s ring buffer. The Mic Feed stream writes
  into it, the Microphone stream reads from it (20 ms prefill, at most 100 ms lag, silence when the
  engine is not feeding it).
* `Source/Main/minwavertstream.cpp`: render streams hand their audio to the cable (Mic Feed) or
  let it go (the four channel outputs). The engine does not need the driver to deliver their audio:
  it records them with WASAPI loopback, which it already does for any output.
* `Source/Main/AudioraVA.inx`: generated by `tools/make_inx.py`. Do not edit it by hand.

The engine needs no setup: `channels::resolve` picks "Audiora Game/Chat/Media/Aux" as the channel
devices and "Audiora Mic Feed" as the processed-mic output as soon as they exist, and never uses
"Audiora Microphone" as its own input (that would be a loop).

Not in v1 (see DESIGN.md): shared-memory rings to the engine instead of loopback, 7.1 for Game,
formats other than 48 kHz, per-endpoint volume state (the sliders of the four outputs share the
sample's one virtual mixer; the engine does not use them), a declarative (DCH) INF: the endpoint
names are still registered under HKLM\...\MediaCategories.

## Keeping it crash-free

A bug in kernel code crashes Windows (blue screen) instead of just one program, so the driver is
kept deliberately small and every change goes through these gates before a package exists:

* **Tiny change set.** Microsoft's sample is a well-tested base; Audiora adds about 150 lines
  (the cable plus the endpoint tables). No allocation, no files, no IOCTLs, no DSP in the kernel.
* **Kernel rules by construction.** The whole audio path runs from non-paged code and data (it is
  called at DISPATCH_LEVEL from the stream timer); the cable takes one spin lock, always *inside*
  the stream's position lock, never the other way round, so there is no lock-order deadlock.
* **The cable is tested with a real compiler** (`scripts\driver-test.ps1`, no WDK needed):
  the exact driver source is compiled into a user-mode program at `/W4 /WX /analyze` and checked
  for prefill, gap-free streaming, jitter, late start, overflow, underrun, restart and two-thread
  races.
* **WDK code analysis** with the driver rules runs on every build, warnings fail it;
  Static Driver Verifier needs the full WDK and is not run yet.
* **Driver Verifier** on the test machine during the first runs (DESIGN.md, verification).

No process can promise that untested kernel code never crashes; these gates are how it gets as
close to that as possible before it ever loads.

## Build

`powershell -ExecutionPolicy Bypass -File scripts\driver-build.ps1`

Needs only Visual Studio 2022 / Build Tools with the C++ workload. The WDK is not installed: the
script downloads Microsoft's WDK and SDK NuGet packages once into `driversirtual-audio\packages`
(git-ignored, about 310 MB) and calls the compiler with the WDK's kernel-driver options. It runs the
cable tests, compiles at `/W4 /WX /analyze` with the WDK driver rules (Microsoft's headers are
excluded, Audiora's code is not), links, stamps and verifies the INF, and test-signs `AudioraVA.sys`
and the catalog with a self-signed "Audiora Test Driver Signing" certificate kept in
`%USERPROFILE%\.audiora\driver-test.pfx` (never committed, never added to a certificate store
by the build). Result: `dist\driver\`. Installs nothing.

Fixes made to the Microsoft sample because the analysis flagged them: memory is never allocated as
executable, a status that was ignored is checked, a NULL output buffer is rejected, the test-tone
writer is bounds-checked, and the sample's demo code that registered the current thread as a stream
resource (and overwrote the endpoint install status) is removed.

## Install (test machine)

Test-signed drivers only load where test signing is on, which is your decision on your machine:

1. Create a System Restore point.
2. Secure Boot off in the firmware settings (some anti-cheat games refuse to run while it is off),
   then elevated: `bcdedit /set testsigning on`, restart.
3. Elevated, in `dist\driver\`: `powershell -ExecutionPolicy Bypass -File .\driver-install.ps1`
4. Settings → System → Sound should list the six endpoints; Audiora picks them up by itself.

To go back: `driver-install.ps1 -Uninstall` (device, package and test certificate), then
`bcdedit /set testsigning off`, Secure Boot on, restart. A virtual machine (Hyper-V, Secure Boot off
in the VM's settings, a checkpoint before installing) is the safer place for the very first load.

## Before anyone else gets it

Kernel drivers for other people's PCs must be signed by Microsoft (Hardware Dev Center, attestation
signing; needs an EV code-signing certificate). Until then the driver only runs on test-signing
machines.
